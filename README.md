# Auth API

REST API для регистрации, авторизации и управления сессиями пользователей. Проект разработан на Node.js с использованием Express, Prisma ORM и SQLite. Для проверки корректности работы реализованы автоматические тесты на Jest и Supertest.

## Возможности

- Регистрация пользователей.
- Хэширование паролей перед сохранением в базу данных.
- Авторизация по email и паролю.
- Выдача access- и refresh-токенов.
- Обновление токенов с отзывом предыдущего refresh-токена.
- Выход из системы и отзыв refresh-токена.
- Получение данных авторизованного пользователя.
- Валидация входящих запросов.
- Централизованная обработка ошибок.
- Автоматические тесты и отчёт о покрытии кода.

## Требования

Для запуска проекта необходимы:

- Node.js (рекомендуется актуальная LTS-версия);
- npm.

Отдельно устанавливать SQLite обычно не требуется: приложение использует SQLite через Prisma.

## Установка и запуск

### 1. Получение проекта

Если проект размещён в Git-репозитории:

```bash
git clone <адрес-репозитория>
cd <папка-проекта>
```

Если проект уже находится на компьютере, откройте его папку в терминале.

### 2. Установка зависимостей

```bash
npm install
```

### 3. Настройка `.env`

В корне проекта создайте файл `.env`. Пример конфигурации:

```dotenv
DATABASE_URL="file:./dev.db"

JWT_ACCESS_SECRET="replace-with-a-long-random-secret"
JWT_REFRESH_SECRET="use-a-different-long-random-secret"

ACCESS_TOKEN_EXPIRES_IN="15m"
REFRESH_TOKEN_EXPIRES_IN="7d"
```

Указанные секреты — примеры для локальной разработки. Для реального использования задайте собственные случайные значения. Не публикуйте `.env` и не добавляйте его в Git.

Если в репозитории есть `.env.example`, используйте его как основной шаблон и заполните все необходимые переменные.

### 4. Подготовка базы данных

Сначала сгенерируйте Prisma Client:

```bash
npx prisma generate
```

Затем примените имеющиеся миграции:

```bash
npx prisma migrate dev
```

Если миграций ещё нет и это первая настройка базы данных, создайте начальную миграцию:

```bash
npx prisma migrate dev --name init
```

Не запускайте команду с `--name init` повторно, если начальная миграция уже создана.

### 5. Запуск сервера

Посмотреть доступные команды можно в `package.json` в разделе `scripts`:

```bash
npm run
```

Если в проекте определён скрипт `start`, запустите:

```bash
npm start
```

Если определён скрипт `dev`, для режима разработки используйте:

```bash
npm run dev
```

После запуска сервер будет слушать порт, указанный в настройках приложения или переменных окружения. Используйте этот адрес при отправке запросов к API.

## API

Основные маршруты проекта:

| Метод  | Маршрут              | Назначение                             |
| ------ | -------------------- | -------------------------------------- |
| `POST` | `/api/auth/register` | Регистрация пользователя               |
| `POST` | `/api/auth/login`    | Вход пользователя и получение токенов  |
| `POST` | `/api/auth/refresh`  | Обновление пары токенов                |
| `POST` | `/api/auth/logout`   | Выход и отзыв refresh-токена           |
| `GET`  | `/api/users/me`      | Получение данных текущего пользователя |

### Регистрация

`POST /api/auth/register`

Пример тела запроса:

```json
{
  "name": "Иван",
  "email": "ivan@example.com",
  "password": "your-password"
}
```

Сервер проверяет входные данные, хэширует пароль и сохраняет пользователя в базе данных. Точный набор обязательных полей и ограничения задаются валидатором проекта.

### Авторизация

`POST /api/auth/login`

Пример тела запроса:

```json
{
  "email": "ivan@example.com",
  "password": "your-password"
}
```

Сервер находит пользователя, проверяет пароль и при успешной проверке возвращает access- и refresh-токены.

### Обновление токенов

`POST /api/auth/refresh`

Клиент отправляет действующий refresh-токен. Сервер проверяет подпись, срок действия и наличие токена в хранилище. Если проверка успешна, старый refresh-токен отзывается, а клиент получает новую пару токенов.

Повторное использование уже отозванного refresh-токена должно завершаться отказом в авторизации.

### Выход

`POST /api/auth/logout`

Сервер отзывает refresh-токен, переданный клиентом. После этого его нельзя использовать для получения новой пары токенов.

### Получение текущего пользователя

`GET /api/users/me`

Маршрут доступен с действующим access-токеном. Токен передаётся в HTTP-заголовке:

```http
Authorization: Bearer <access-token>
```

В ответ сервер возвращает данные пользователя, которому принадлежит токен.

## Как работает авторизация

В проекте используется пара JWT-токенов с разным назначением.

**Access-токен:**

- используется для доступа к защищённым маршрутам;
- передаётся клиентом в заголовке `Authorization`;
- имеет относительно короткий срок действия.

**Refresh-токен:**

- используется для получения новой пары токенов;
- имеет более длительный срок действия;
- хранится на сервере в виде хэша, чтобы сервер мог проверять и отзывать выданные токены.

Основной сценарий работы:

1. Пользователь отправляет email и пароль на `/api/auth/login`.
2. Сервер проверяет пароль и выдаёт access- и refresh-токены.
3. Клиент отправляет access-токен при обращении к защищённым маршрутам.
4. Когда access-токен истекает, клиент отправляет refresh-токен на `/api/auth/refresh`.
5. Сервер проверяет refresh-токен, отзывает его и выдаёт новую пару.
6. При выходе пользователь отправляет запрос на `/api/auth/logout`, после чего refresh-токен отзывается.

Пароли не сохраняются в открытом виде: перед записью в базу данных они хэшируются с помощью bcrypt. Для подписи access- и refresh-токенов используются разные секретные ключи.

## Тестирование

Для автоматической проверки проекта используются **Jest** и **Supertest**.

- **Jest** запускает тестовые файлы, выполняет проверки и формирует отчёт о покрытии кода.
- **Supertest** отправляет HTTP-запросы к Express-приложению во время тестов. Благодаря этому тесты могут проверять API без ручного запуска сервера в отдельном терминале.
- Тесты проверяют корректные сценарии и ошибки: регистрацию, авторизацию, обновление токенов, повторное использование отозванного refresh-токена, валидацию входных данных и другие реализованные случаи.

### Запуск всех тестов

```bash
npm test
```

Команда выполняется при наличии скрипта `test` в `package.json`.

### Запуск тестов с покрытием

```bash
npm run test:coverage
```

Эта команда запускает тесты и выводит статистику покрытия кода.

Основные показатели:

| Метрика    | Значение                           |
| ---------- | ---------------------------------- |
| Statements | Процент выполненных инструкций     |
| Branches   | Процент проверенных ветвей условий |
| Functions  | Процент вызванных функций          |
| Lines      | Процент выполненных строк кода     |

После запуска Jest может сформировать каталог `coverage` с подробным отчётом. Если включён HTML-отчёт, его можно открыть в браузере:

```text
coverage/lcov-report/index.html
```

### Запуск отдельного тестового файла

Чтобы запустить только тесты авторизации и обновления токенов:

```bash
npx jest tests/auth.refresh.test.js
```

Чтобы запустить только тесты валидации:

```bash
npx jest tests/validation.test.js
```

Путь и название файла должны совпадать с фактическими файлами в каталоге `tests`.

### Если тесты не запускаются

1. Убедитесь, что зависимости установлены: `npm install`.
2. Проверьте, что файл `.env` создан и содержит необходимые переменные.
3. Убедитесь, что Prisma Client сгенерирован: `npx prisma generate`.
4. Проверьте, что тестовые команды действительно объявлены в `package.json`:

```json
{
  "scripts": {
    "test": "jest",
    "test:coverage": "jest --coverage"
  }
}
```

Это пример настройки. Не заменяйте весь раздел `scripts`, если в проекте уже есть другие команды: при необходимости добавьте только отсутствующие скрипты.
